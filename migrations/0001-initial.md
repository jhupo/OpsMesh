# 0001 — Initial storage

The initial revision installs these infrastructure structures:

| Structure | Owner | Purpose |
| --- | --- | --- |
| `opsmesh_schema_versions` | Infrastructure migrations | Applied version and fingerprint of each registered table |
| `opsmesh_outbox` | Infrastructure event delivery | Durable event envelopes, retry schedule, delivery lease and dead-letter state |
| Module record tables | The module that registers each table | Versioned JSON data with ID, revision and UTC creation/update timestamps |

`VersionedRecordStore` validates JSON portability, enforces a positive revision in the
database, and uses a conditional revision update/delete to prevent lost writes.
Create, update and delete can append outbox events using the **same database transaction**.
An invalid event or duplicate event ID rolls back the associated record mutation.
The same `(record ID, expected revision)` must not be reused after a conflict without
re-reading and applying the module's domain rules.

Event envelopes retain extension fields. Missing IDs and timestamps are generated by
the writer. The required canonical fields are `id`, `type`, `source`, `payload`,
`schema_version` and an aware ISO timestamp `occurred_at`. Legacy `subject` fields remain
present and are also copied into `payload` without replacing canonical payload fields.

Workers call `claim_events(owner, limit, lease_seconds)`, then acknowledge or reject with
the same owner. PostgreSQL uses row locking with `SKIP LOCKED` and conditional updates;
SQLite serializes claims with `BEGIN IMMEDIATE`. Use a unique owner for each delivery
batch, renew leases before a long handler exceeds them, and do not reuse an expired
owner for a later batch. `pending_events()` is only an inspection/legacy API and does
not reserve work. Rejected events receive exponential retry delay capped at 300 seconds.
Events that exhaust the configured attempt count enter dead-letter state, including
repeated worker crashes without an explicit rejection. Operators can inspect
`dead_letters()` and explicitly `requeue_event(id)` after correcting the cause.

Delivery is **at least once**. A process can perform an external action and crash before
acknowledging it; a consumer must deduplicate by the stable event ID or use an idempotency
key with the downstream service. Leases prevent concurrent valid claims, but cannot
revoke an already-running external request after a worker stalls past its lease.

The generic JSON store is a pragmatic first storage implementation, with explicit limits:

- DTO/schema validation and cross-record references belong to the owning module. A
  generic record does not create relational foreign keys for IDs inside JSON.
- Revision CAS is atomic for one record. The store does not promise a domain transaction
  spanning several independently called record stores. Complex domain changes must
  choose a single aggregate or introduce an explicit transaction-oriented repository.
- Query indexes cover IDs and creation order. Arbitrary JSON-field filtering currently
  happens in modules and may scan rows; large installations need module-specific SQL
  tables, indexes and paginated public queries before scaling those workloads.
- The usage ledger intentionally keeps one principal's observations, costs and
  reservations in one CAS aggregate to avoid partial accounting. A busy principal is
  a contention point, and unbounded observation retention is unsuitable for large
  deployments. Partitioning/retention requires a future ledger migration preserving
  idempotency and accounting invariants.
- SQLite is intended for local development or small single-host deployments. PostgreSQL
  is the production database target. Automated tests cover real SQLite transactions,
  cross-instance contention and PostgreSQL DDL compilation; a passing compile test is
  not evidence of a live PostgreSQL integration run.

No production data backfill exists for this initial revision. Existing unversioned
databases require a separately reviewed import/migration instead of automatic adoption.
