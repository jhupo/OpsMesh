# OpsMesh 0.2.0

此版本发布 Agent 执行、编排、插件和消息网关框架更新。
服务端、插件 SDK 和运维 CLI 统一为 0.2.0。
生产部署继续使用预构建 Docker 镜像或包含运行时的本机二进制包。

## 主要变化

- 自研网关按 API、通道、身份、路由、消息、存储和适配器分类。
  内置 QQ、钉钉；其他通道通过插件扩展。
- 持久消息合批、会话顺序处理、分群策略与短期上下文、占位和 typing、
  发送限流、已知会话广播、QQ 扫码绑定和 QQ C2C 流式文本。
- 普通执行与 Temporal 共用已授权模型绑定，保留不同子 Agent 的模型设置和网络路由。
- 使用官方 Temporal Agents 流式集成；限制公开增量范围，编排 Agent 节点可接收原生消息。
- 统一当前用户校验、Agent 图解析和跨模块依赖注入；修复网关审计来源错误造成的事务回滚。
- 更新插件通道合同，提供可单独安装的 TypeSafe 决策插件示例。
  框架不自动安装该插件，不内置用户的通道或模型凭据。

## 安装资产

在 [v0.2.0 发布页](https://github.com/jhupo/OpsMesh/releases/tag/v0.2.0)下载
`install.sh`、Linux amd64 服务端和适合本机的运维 CLI。
Docker API、Worker、Runtime 镜像由 `release-manifest.json` 固定 digest；
原生目录包包含必要运行时，不需要目标机器安装 Python、pip 或 uv。
Python wheels 和 sdists 面向开发；GitHub 自动生成的 Source code 包不用于部署。
平台矩阵、摘要和来源验证见[发行格式](../../deploy/DISTRIBUTIONS.md)。

## 从 0.1.0 升级

1. 备份数据库、Temporal、文件、插件和密钥，先在隔离环境演练升级。
2. 暂停入口并处理旧 Agent Workflow、审批和未决外部效果，再切换 API、Worker 和 Gateway。
   当前模型引用及流式路径发生变化，未验证旧历史的跨版本重放，不能热替换存量执行。
3. 使用发行安装器迁移数据库至 `0006_gateway_processing`，然后启动新进程。
   旧通道的日常配置和插件热更新仍不要求整个服务重启。
4. 插件按 0.2 SDK 重新检查、打包和安装。ContentPart 只允许一个媒体来源；
   原网关内部模块路径已移除，不提供兼容包装。

持久实例、Session、沙箱和目录不会因为 Run 完成而自动删除。
迁移降级检查不等于允许二进制直接回退；回退应使用[协调恢复流程](../../deploy/server/delivery-operations.md)。

## 验收和限制

发布前工作区验收包括 283 项 Linux 非模型回归、SDK 6 项、运维 CLI 17 项，
以及单独运行的真实模型工具调用、持久 Agent 普通/流式执行和同版本 Temporal 重放。
真实 PostgreSQL 迁移升降级、ORM 比较、Docker 沙箱边界、静态检查和干净 wheel 检查通过。
这些结果属于工作区；本次二进制和镜像须另外通过 tag 触发的构建及部署验收后发布。
完整证据见[验收记录](../acceptance.md)。

- 上游模型曾出现 TLS 连接失败、HTTP 524 和请求超时；后续复核通过不保证其持续可用。
  外部效果不确定时保留对账状态，不自动重复整个 Run。
- QQ/钉钉真实收发、扫码、重连和厂商消息额度未在本轮验收。
- TypeSafe 经指定代理的真实决策、外部 MCP 热更新恢复，以及复杂编排故障恢复仍有覆盖缺口。
- SandboxAgent 的完整模型写代码、审批、取消与 Worker 重启组合流程未在本轮完整验收。
- 不包含 Web 管理界面、企业 SSO、组织管理、内置知识库或插件市场；
  服务端仅支持 Linux amd64，沙箱不提供跨 Docker daemon 故障转移。

本次发布交付上述框架能力，未将未验收的厂商连接或复杂恢复场景声明为已通过。
