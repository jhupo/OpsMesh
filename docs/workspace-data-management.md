# Workspace Data Management

## Goal

Users must be able to upload and download workspace data. Uploaded data becomes workspace-scoped input for agents, tools, MCP workflows, and Docker runtimes. Downloaded data must go through authorization, audit, and controlled export.

The product should treat files as first-class workspace resources, not anonymous blobs.

## Data Types

### Workspace Files

Files uploaded by users or imported from connectors.

Examples:

- PDFs
- CSVs
- spreadsheets
- documents
- images
- datasets
- source archives
- reference materials

### Artifacts

Files generated by agents, tools, runtimes, or workflows.

Examples:

- reports
- generated images
- edited images
- charts
- transformed datasets
- code patches
- rendered documents
- logs

### Runtime Files

Temporary files staged into Docker runtimes for execution.

Examples:

- task working directory files
- local skill helper outputs
- intermediate scripts
- temporary transformed data

Runtime files are not durable until collected as artifacts or workspace files.

## Core Rules

- Every file belongs to exactly one workspace.
- Every file record includes `workspace_id`.
- Downloads require workspace membership and permission checks.
- Uploads create durable metadata in Postgres.
- File bytes are stored in controlled storage, not directly in arbitrary host paths.
- Docker runtimes receive only explicitly staged workspace files.
- Runtime outputs become downloadable only after artifact collection and authorization.
- File access must be logged for sensitive downloads and all agent-generated exports.

## Storage Model

MVP can use local object storage paths managed by the backend. Later, the same abstraction can move to S3, R2, GCS, MinIO, or Azure Blob.

Recommended logical path format:

```text
workspaces/{workspace_id}/files/{file_id}/{safe_filename}
workspaces/{workspace_id}/artifacts/{artifact_id}/{safe_filename}
workspaces/{workspace_id}/runs/{run_id}/logs/{log_id}.txt
```

Do not expose these paths directly to users as authorization tokens.

## Upload Flow

1. User requests upload in a workspace.
2. API validates workspace membership and upload permission.
3. API creates `workspace_files` row with `uploading` status.
4. Client uploads bytes through backend stream or pre-signed upload URL.
5. Backend verifies size, content type, and checksum.
6. Backend stores the object under workspace-scoped storage key.
7. Backend marks file `available` or `quarantined`.
8. Backend writes `file_access_events` and `audit_events`.
9. Optional worker extracts text, previews, metadata, or embeddings.

MVP can start with backend-streamed upload. Pre-signed upload can come later for large files.

## Download Flow

1. User requests file or artifact download.
2. API validates workspace membership and download permission.
3. API verifies the resource belongs to the workspace.
4. API writes access event.
5. API streams the file or issues a short-lived signed URL.

Download URLs must expire quickly and must not grant access across workspaces.

## Preview Flow

Preview should be separate from download.

Examples:

- text preview
- image preview
- PDF thumbnail
- CSV sample
- document metadata

Preview access still requires workspace permission and should avoid loading very large files into API memory.

## Runtime Staging Flow

Agents and tools should not mount all workspace files.

1. Worker determines which files are required by a task or tool call.
2. Orchestration validates the agent can access those files.
3. Runtime Manager copies or mounts only approved files into the runtime directory.
4. Runtime command executes inside Docker.
5. Runtime Manager collects selected outputs.
6. Outputs become artifacts.
7. Artifacts are stored under workspace-scoped storage keys.

Runtime paths should be internal details, not permanent file identifiers.

## Artifact Collection

Artifact collection should be explicit.

Rules:

- Do not automatically publish every runtime file.
- Collect only files matching policy or tool output declarations.
- Enforce artifact size limits.
- Compute checksum.
- Store artifact metadata in Postgres.
- Attach artifacts to task and run.
- Write access and audit events.

## Permissions

Initial file permissions:

- `file.upload`
- `file.read`
- `file.download`
- `file.delete`
- `artifact.read`
- `artifact.download`
- `artifact.delete`
- `runtime.stage_file`
- `runtime.collect_artifact`

Role defaults:

- owner: all file and artifact permissions
- admin: all except hard delete if added later
- operator: upload, read, download, use in task
- viewer: read and download, depending on workspace policy

Agent permissions are separate:

- allowed file scopes
- allowed artifact write types
- allowed runtime staging
- maximum file size
- allowed content types

## Security Requirements

- Sanitize filenames.
- Store files by generated IDs, not raw filenames.
- Verify resource `workspace_id` on every access.
- Enforce upload size limits.
- Enforce content type policy.
- Compute checksums.
- Avoid direct host path exposure.
- Quarantine suspicious or unsupported files.
- Do not pass uploaded files to Docker until explicitly staged.
- Log downloads and runtime staging.
- Prevent path traversal in archives.

## Data Export

Users should be able to export workspace data.

Initial export types:

- task result export
- artifact download
- selected files download
- run log export
- workspace metadata archive export

Implemented metadata export:

- `POST /api/v1/workspaces/{workspace_id}/exports/metadata`
- exports workspace, agents, teams, tasks, runs, file/artifact metadata, and audit metadata as JSON
- enforces workspace authorization
- records `workspace.export.created`

Implemented metadata import:

- `POST /api/v1/workspaces/{workspace_id}/exports/metadata/import`
- supports dry-run by default
- imports agents, teams, team members, tasks, and task steps into the target workspace
- keeps imported tasks as drafts and does not enqueue runs automatically
- records `workspace.import.created` on committed imports

Implemented archive export:

- `POST /api/v1/workspaces/{workspace_id}/exports/archive`
- returns a zip with `metadata.json`
- can include workspace file bytes under `files/{file_id}/{filename}`
- can include artifact bytes under `artifacts/{artifact_id}/{filename}`
- enforces per-object and total archive byte limits
- writes `skipped-objects.json` when storage objects are missing or too large
- records `workspace.archive_export.created`

Implemented archive import:

- `POST /api/v1/workspaces/{workspace_id}/exports/archive/import`
- accepts a workspace archive zip upload
- reads `metadata.json` and reuses metadata import
- can restore workspace file bytes into the target workspace
- can restore artifact bytes into the target workspace and remap artifacts to imported tasks when available
- supports dry-run, per-object byte limits, and total restored byte limits
- records `workspace.archive_import.created` on committed imports

Workspace metadata archive export can include:

- tasks
- task steps
- final outputs
- selected artifacts
- run summaries
- audit metadata

Large full workspace exports with file bytes should be moved to async jobs because they may be large.

## Data Deletion

MVP deletion can be soft delete.

Rules:

- Mark file or artifact as deleted in Postgres.
- Hide deleted files from normal retrieval.
- Keep audit record.
- Clean physical bytes later with a cleanup job.
- Do not delete files that are still required by active runs unless policy allows cancellation.

## Integration With Agents

Agents should access files through tools, not direct paths.

Useful product tools:

- `list_workspace_files`
- `read_workspace_file`
- `search_workspace_files`
- `stage_file_to_runtime`
- `write_artifact`
- `list_task_artifacts`

Each tool enforces workspace and agent permission checks.

## MVP Scope

For the first backend implementation:

- backend-streamed upload
- workspace file metadata table
- local storage adapter
- artifact table
- authorized download endpoint
- runtime staging for selected files
- artifact collection from Docker runtime
- access events

Later:

- pre-signed uploads
- object storage backend
- file previews
- virus scanning
- embeddings/indexing
- bulk export
- retention policies
