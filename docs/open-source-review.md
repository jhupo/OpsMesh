# 开源就绪审查

本次检查覆盖当前工作区的包边界、安装入口、发布流程、文档和许可入口。最初审查在无 Git 历史及 GitNexus 索引的开发目录完成；整理后的项目已同步到 [jhupo/OpsMesh](https://github.com/jhupo/OpsMesh) 工作区，但尚未形成已提交的发布版本。此文记录可核实的工程边界，不代替安全审计或发布验收。

## 本次修正的发布障碍

| 问题 | 影响 | 修改方向 |
|---|---|---|
| 核心包发现规则包含所有插件，核心依赖包含 SDK 与数据库 | 无法单独安装和部署框架，插件实际上不可独立发布 | 核心与四插件使用独立发行定义、源码目录和依赖 |
| 安装器强制执行 database 命令并提供迁移选项 | 空宿主部署依赖数据库，部署框架会触及插件业务 | 默认空清单，只执行通用宿主检查；插件迁移独立执行 |
| tag 工作流只上传合并后的 Linux 包 | 插件没有可独立获取的发布附件 | 同 tag 发布五个 Python 包和独立 Linux 插件运行包 |
| README 仍描述 execution 用量落库、旧目录和互相覆盖的方案 | 用户无法判断真实接口和安装要求 | 更新 README，保留当前架构与契约，移除过时整改和清理流水记录 |
| 缺少贡献、安全报告和版本变更入口 | 外部贡献者缺少验证及报告方式 | 添加 CONTRIBUTING、SECURITY 和 CHANGELOG |

每项是否满足发布条件应以本次产物检查和 CI 运行结果为准，不能仅凭新增配置文件判断。

## 公开发布前仍需确认

- **仓库与发布身份**：仓库地址已确认是 `https://github.com/jhupo/OpsMesh`；仍需确认 Actions 权限与维护设置。当前流程不向 PyPI 发布。
- **可执行产物验证**：Linux 两种架构需分别验证框架空启动、外部插件加载、SDK 所需资源、原生依赖、systemd 安装及回退。Windows 单元测试不能证明 Linux 二进制可运行。
- **外部服务验收**：PostgreSQL、QQ、钉钉、模型供应商、MCP 与 Langfuse 的兼容性应按实际发布版本记录。确定性模型测试不能替代供应商联调。
- **漏洞报告入口**：公开仓库启用私密漏洞报告，并由维护者决定是否提供专用安全联系地址；目前没有响应 SLA。
- **版本策略**：现有同步版本适合初期发布；发布前稳定文档中公开的调用契约。未来独立升级插件时需要单独制定兼容矩阵，不能只放宽依赖范围。
- **依赖与许可证**：核心及插件的依赖锁和许可信息需要随每次升级复核；MIT 项目许可不覆盖第三方资源的不同许可。

## 已明确的运行限制

源码插件是进程内受信任代码，不支持不可信 Python 隔离或同进程热替换。机器人接收缓冲不是持久队列，进程退出可能丢失已确认事件。默认 API 不提供业务会话或 Agent 管理中心。

当前锁定 OpenInference 与 SDK 的审批恢复存在追踪边界，见 [Langfuse 说明](langfuse-tracing.md)。数据库共享历史升级需要管理员提供完整来源，见 [数据库迁移](database-migrations.md)。这些限制应随版本说明对外公开，不能用“框架已支持”概括所有业务能力。
