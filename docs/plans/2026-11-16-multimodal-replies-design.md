# 多模态回复与模型交付物设计

状态：本地实现及受影响自动化验证已完成，尚未发布或部署。第 15 节记录实际支持范围和验证边界；第 12 节保留完整验收要求，不能将自动化通过理解为真实机器人或服务器已验收。

## 1. 目标与边界

一次智能体回复能够按顺序交付普通文字、Markdown、表格、图片、文档、音频和视频；支持完整发送与渐进发送。模型产物有真实来源、明确归属和可查询的交付记录。任何格式识别都来自类型、工具约定或文件验证，不从自然语言猜测。

完整方案包括内容契约、原生产物接入、文件登记、持久交付记录、消息转换、传输、错误语义、示例和部署迁移。框架不增加 Agent、Session、文件目录或业务结果数据库；execution 继续返回原生 RunResult/RunResultStreaming。

采用现有框架 Message/MessageSegment 与 Channel/Matcher 扩展点。参考 NoneBot 的组合消息、LangChain 的有序内容块及 Agents SDK 的原生结果/运行条目。无需引入 LangChain 依赖。

## 2. 迁移前实现与替换目标

| 当前实现 | 目标 |
|---|---|
| conversation_support.streaming.text_deltas 只接收文本，最终结果必须是 str | 单一 SDK 事件消费者，识别公开内容、交付物和结构化结果 |
| stream 接收 AsyncIterator[str]，整条流附带一个 format | stream 接收明确的消息开始、文本增量、消息结束及完整 Message |
| 示例把所有模型回答标为 Markdown | 调用插件指定文本策略；结构化结果由专用输出处理器转换 |
| 调用插件临时登记附件，未形成交付记录 | 显式交付集合、持久文件引用和交付回执 |
| MessageSegment.data 接受通用映射，部分类型仅在发送时检查 | 保留框架抽象，channels 入口按各消息段 schema 严格校验 |
| 表格仅可能出现于字符串或 data 中 | 明确的 table 消息段，以及可查验的通道转换策略 |
| 平台原生回执及分段失败信息 | channels 统一描述已确认、失败和结果未知，保留原生回执 |

删除旧 text_deltas 和字符串流入口，调用方及测试同步迁移。不保留格式猜测、旧参数别名、双协议或隐藏回退。普通字符串仍是 send 的正式纯文本类型，不属于兼容分支。

## 3. 依赖与职责

| 组件 | 职责 |
|---|---|
| framework | Event/Message 抽象、on_*、Matcher.send/finish、Depends、插件归属、准入与排空 |
| execution | 原生 Runner、回调、取消和 tracing；不认识 channels 的交付结构 |
| channels | 通用消息结构、附件读取限制、传输流元素、协议转换与发送结果 |
| filesystem | 受限文件读写和目录操作；不识别用户、Agent、知识库或交付状态 |
| 智能体插件 | 构造 Agent、消费原生 SDK 结果、选择公开内容与发布策略、提供结构化转换和受限文件工具、持久化交付记录和历史引用 |
| examples / conversation_support | 演示智能体插件的接入；可共享示例自身的输出处理、会话和存储代码，不成为生产插件的运行依赖 |

通用交付集合属于 channels，非智能体业务也能使用。SDK 输出解析、产物选择、沙箱 publish_file 工具和发布策略属于智能体插件内部，不新增输出插件、独立发行包或插件加载入口。

依赖方向为 `智能体插件 → execution + channels`，需要持久文件时再依赖 filesystem，需要数据库时再依赖 database。智能体插件直接使用原生 SDK 类型；execution 不导入 channels，channels 不导入 SDK，filesystem 不认识交付记录。通过框架 require 声明依赖、Depends 管理调用资源、on_* 接收事件，完整消息通过 Matcher.send/finish 回复，流式通过现有 Channel.call 入口交付。

职责判断依据是行为由谁决定：哪些模型内容可以公开、哪些文件属于成果、何时发布以及保存多久，都由智能体插件决定。同时使用 SDK 与 channels 是它的正常职责，不构成新增插件的理由。只有与智能体无关的消息校验、附件读取限制、平台编码与回执才放入 channels。

示例允许包含自身的输出处理代码；纯文本插件直接读取原生 final_output 后构造 Message，无需实现所有产物处理能力。支持沙箱或结构化输出的插件按实际需要增加内部模块，不强制实现统一输出基类、工厂或注册中心。

## 4. 内容契约

继续使用 Message 作为有序 MessageSegment 序列，不再定义平行的 AgentReply 或新 RunResult。

| 消息段 | 必需内容 | 语义 |
|---|---|---|
| text | text | 普通文字，保留原文 |
| markdown | text；可选 title | 明确使用 Markdown，渲染受接收端限制 |
| table | columns、rows；可选 caption | 结构化表格；行列维度和单元格类型受校验 |
| image | attachment_id；可选 alt | 实际图片附件 |
| file | attachment_id | 文档、压缩包及其他原始文件 |
| audio/video | attachment_id 与平台必需的真实媒体信息 | 沿用已有音视频约束 |
| mention | 已验证的用户引用 | 平台支持时转换；不伪造用户身份 |
| data | JSON object | 面向调用程序的结果，机器人不把它自动当显示内容 |

table 的单元格限定为字符串、数字、布尔值或 null，不允许嵌套执行对象；限制行数、列数和总序列化字节。单元格文本不能被当作 HTML 或代码执行。展示表格与 CSV/XLSX 附件可以同时出现。

Markdown 中的图片链接不自动变成附件；字符串中的路径不自动读取。HTML、SVG 等默认作为明确文件交付，HTTP 下载维持 attachment 与 nosniff；需要图片预览由工具产生对应的安全图片格式。

完整 Message 在首次可见发送前完成类型校验、附件归属/存在性检查、转换和发送数量预算。限制作用于实际转换后的内容，防止表格转文本或拆分后绕过限额。

## 5. 模型产物如何进入交付集合

### 5.1 调用级 Deliverables

智能体插件需要文件交付时，在自己的代码中建立独立的 Deliverables，绑定本次附件集合与已认证的调用归属。普通文本、Markdown 或无附件表格直接构造 Message，不要求创建交付集合。调用插件用框架 Depends 组合本次资源，不另建依赖容器。工具通过本次构造的闭包获得该集合。不得存入全局变量、共享 Agent 可变字段或 UserContext。

拟定操作：

- add：登记工具/SDK 已经提供的真实内容，得到引用；默认不发送。
- select：仅将内容已固定的附件引用加入本次交付清单，确定显示类型、描述和顺序；尚未完成读取的引用不能被选中。
- get：只能查询本次允许使用的引用。
- entries：获取已选择的不可变清单，用于消息构造和保存。

同一个附件 ID 可以被多个消息引用；智能体插件对同一 SDK 来源的自动采集去重。channels 不识别 SDK item ID、工具调用 ID 或 handoff，也不维护它们到附件的映射。重复发送由调用方显式选择，不能把用户有意发送两次的内容按文件哈希静默删除。

并行工具只登记，不直接竞争发送。输出适配器按预先确定的工具调用位置和插件指定的显示顺序提交内容；完成较早不意味着排在前面。默认最终附件在正文结束后按声明顺序交付，需要插入正文之间时由输出结构明确指定位置。本次闭包工具通过原生 Agent 的调用级副本/构造接入，不能修改共享 Agent.tools 来绑定当前用户资源。

附件集合保存字节或受限读取器；Deliverables 只保存通用附件引用、有序选择及描述，不复制另一份二进制缓存。SDK 来源映射、工具位置与去重状态由智能体插件自己的输出处理模块持有。现有接收附件的 add 与输出附件的 add_bytes 要明确分配额度，不能借用接收登记接口引入输出加载器而绕过输出总量限制。读取器在沙箱退出前必须完成物化或持久化。

选入交付清单之前，必须完成受限读取并固定内容：使用不可变字节，或调用插件拥有的不可变文件副本，同时记录实际大小和校验和。持久化、媒体上传和 HTTP 下载复用这份内容，不能分别按原路径再次读取。读取时按实际字节计量，在超过限制时立即停止；读取完成后才能确认交付引用，不以预先 stat 的大小替代真实读取限制。

沙箱原文件在选择后可以继续修改，但既有交付引用不随之变化；需要交付修改后的内容时生成新引用。并行工具修改同一文件时，插件须与写入方协调或使用后端可靠快照，不能把不一致的读取称作完整文件。延迟读取器仅用于尚未选择的候选内容；选择失败不能留下可发送或可下载的半成品。内容固定本身不等于允许公开，仍受第 9 节发布检查约束。

### 5.2 三种真实来源

| 来源 | 接入方式 |
|---|---|
| 自定义原生 SDK 工具 | 工具完成后登记内容；需要对用户交付时显式 select；返回真实附件引用供模型引用 |
| 原生图像生成、文件输出 | 智能体插件按自己支持的 SDK 类型提取完成产物；base64 在解码前检查上限，远程文件标识交给调用插件提供的受限读取器；保留来源 item ID |
| 沙箱文件 | 智能体插件在自己的 tools/files.py 中按原生 SDK 方式定义 publish_file，绑定本次交付集合与受限沙箱读取能力 |

publish_file 只接受本次已开放输出根目录下的文件。调用插件提供与实际后端匹配的读取函数，在实际读取边界检查路径规范化、符号链接/替换逃逸、大小与存在性；智能体插件检查文件是否允许交付，channels 的附件入口统一校验内容、类型与额度，再登记并由插件选择文件。沙箱读取函数使用所属 SDK SandboxSession，不能按宿主路径读取。SDK 后端无法证明路径边界时拒绝该读取，不声称仅做字符串前缀检查即可安全导出。

文件、MCP 及供应商客户端的凭据和生命周期仍由调用插件持有。输出处理复用插件持有的客户端和受限读取能力，不读取任意 URL，也不假设所有供应商 file_id 都能用 OpenAI Files API 下载。请求公开的未知产物类型明确报告不支持；新增来源需要显式适配和对应测试。与交付无关的未知内部 SDK 事件可以保留为观测数据，既不自动公开，也不因此拒绝整个合法运行。

工具返回给模型看的图片、MCP 资源、检索文档不自动成为交付物。业务工具需要通过显式选择表明发送意图。工具执行成功、文件登记成功和消息发送成功是三个不同事实。

模型最终说“已生成”或编造文件 ID 都不作为登记依据。结构化输出引用附件时，只能引用真实交付集合；非法引用应报输出校验失败。

### 5.3 原生结果与结构化输出

不强制所有 Agent 使用平台 output_type。普通文本采用调用插件明确配置的 text/markdown 策略；原生 structured output 由插件提供对应类型的转换器，返回 Message。未知结果类型明确拒绝，禁止 str(result) 或任意 JSON 猜测转换。

原生 SDK 流只有一个消费者。按 response/item/content index 跟踪内容身份，区分正文、工具调用、工具结果、handoff、审批及 reasoning。仅公开的助手正文和已选交付物进入消息输出，不转发原始事件全集。原生完成项可补齐内容，但不能重复发送已经输出的增量。

公开正文的选择规则由智能体插件自己的输出处理模块执行。默认 buffered 仅发布完成运行后的最终回答及选定交付物，避免把工具轮次的助手说明当作最终答案。progressive 需要调用插件明确允许当前助手正文提前发布；handoff 后的新正文维持独立身份，子智能体工具输出不默认广播。结构化 final_output 只能在原生校验完成后转换，不能把中间 JSON token 当作面向用户的文字流。

### 5.4 公共能力与插件内部调用

| 所在位置 | 接口或职责 | 约定 |
|---|---|---|
| channels | Message、MessageSegment、传输流元素 | 通用内容契约、附件访问与实际发送，不依赖 SDK |
| execution | run / stream | 原样返回 SDK 结果，保持现有执行与清理边界 |
| 智能体插件 conversation.py | 一次对话的执行与发送协调 | 取得调用资源，执行 Agent，选择完整或流式交付 |
| 智能体插件 outputs.py | 结果和流转换 | 读取原生结果，处理公开正文、结构化输出、产物身份与去重，产生通道内容 |
| 智能体插件 tools/files.py | 原生 publish_file 工具 | 仅在提供沙箱文件交付时定义，绑定本次实际读取能力 |
| 智能体插件 deliveries.py | 文件与交付记录保存 | 仅在需要历史交付查询时实现，不规定所有插件的存储方式 |

这些内部模块是职责划分，不是必须实现的公共协议，也不要求定义 AgentOutput 或 SandboxFiles 类。简单处理可以是函数；需要保存本次来源身份和去重状态时使用调用级对象，不能为每次转换增加一层插件或全局注册。

同一个原生结果只有一个交付消费路径，不能流式消费后又完整发送造成重复。输出处理负责转换，conversation 负责协调发送；原生运行由包围它的 execution.stream 或调用者 SDK 作用域关闭。消费中断须关闭输出迭代器，不能返回已脱离资源作用域的源流。

结构化转换由定义 output_type 的智能体插件实现，文件读取由持有对应后端资源的插件实现。资源通过现有 Depends 组合后传入，不放入 UserContext，也不新增依赖容器。

## 6. 完整多模态流契约

Channel.call("stream", event=event, source=...) 保持框架入口，source 的元素改为下列确定类型：

| 元素 | 内容 |
|---|---|
| StreamMessageStart | message_id、format(text/markdown)、可选 title |
| StreamTextDelta | message_id、sequence、text |
| StreamMessageEnd | message_id |
| Message | 已完成的组合内容，例如图片、表格、文档 |

这三种流事件是现有通道 message_start/message_delta/message_end 的类型化契约，不镜像 SDK 事件或运行状态。

一次 source 允许多个文字块和完整 Message 顺序交错；同一时刻只允许一个打开的文字块。开始/结束必须配对，ID 不重复，sequence 连续。插入完整 Message 前先结束当前文字块。格式在开始时确定，不能中途从 text 切换为 Markdown。

通道有界消费，慢发送向适配迭代器施加背压。该保证仅覆盖 channels 与智能体插件输出处理自身的缓冲，不能据此声称原生 SDK 的生产任务也会停止。实现前核对锁定 SDK 的内部事件队列：若存在独立生产任务和无界队列，则使用一个受本次调用管理的消费任务及时排空原生事件，对公开输出设置累计预算与发送停滞超时；无法持续交付时取消原生运行，不丢弃中间内容继续执行。禁止读写 SDK 私有队列或复制 Runner。

本轮检查的已安装 SDK 在 `agents/result.py` 中以不带 maxsize 的 asyncio.Queue 初始化事件队列，且运行循环使用 put_nowait，因此上述限制确实适用。内部实现只作为风险判断依据，不成为公共适配器依赖。预算或停滞触发时使用 SDK 公开取消接口，最终等待与资源关闭仍归本次执行作用域负责。

适配器自身若使用队列，必须有容量、关闭和失败传播约束，消费任务与发送任务在同一调用作用域退出，不留下后台任务。默认限制总体执行时间和公开输出总量；原生 SDK 内部瞬时内存仍需压力验证，文档不得承诺整个进程内存绝对有界。智能体插件将原生 SDK 输出转换成这个 source，channels 只消费通道契约。

例：开始分析说明 → 多个文字增量 → 结束文字 → 完整图片消息 → 完整表格消息 → 开始补充说明 → 结束文字 → 完整文档消息。

HTTP 沿用现有 SSE 名称和消息 ID。完整 Message 输出为 message，文字块使用 start/delta/end。source 正常结束且调用清理成功后由已有 HTTP 请求层发送 done；SDK 正常结束不等于整次用户请求已经完成。JSON 模式按相同顺序有界收集，类型不能丢失。

文字块的 message_id 由输出适配器分配；完整 Message 的 ID 由通道在发送前分配。通道对二者在当前输出中的唯一性进行统一校验，最终回执带相同 ID。持久化关联使用调用插件的 reply ID 和确定的内容位置，不依赖平台回执 ID 才能创建发送前记录。

流式和完整发送必须使用同一份内容校验和通道转换规则。流式只能预检已到达的内容，不能承诺整个回答原子发送。

source 的数量、单个增量、累计文本字节、完整内容字节、附件数量和未完成消息长度均有独立上限。平台拆分计入本次回复发送次数；在已发送部分之后才发现超限时返回部分失败，不能把后续内容静默截断。钉钉卡片数量也计入同一预算。

## 7. 渲染和通道能力

send_types 表示已实现的完整消息类型，stream_formats 表示当前连接配置支持的增量格式。智能体插件据此选择内容表达和是否缓冲；适配器仍检查平台限制，不承诺账号权限或剩余额度。

| 内容 | HTTP | 钉钉 | QQ |
|---|---|---|---|
| text | typed segment/SSE | 文本消息 | 文本消息 |
| markdown | 保留源格式 | Markdown 消息；配置卡片时可增量更新 | 不接受 Markdown 段；插件显式转为文本或文件 |
| table | columns/rows | 插件转为文本或文件后发送 | 插件转为文本或文件后发送 |
| image/file | 认证下载引用 | 素材上传及原生模板 | 官方素材上传及原生媒体消息 |
| audio/video | 文件及媒体元数据 | 支持格式内的原生发送 | 支持格式内的原生发送 |

转换由智能体插件显式完成，通道不持有展示策略、不自动降级。转换辅助函数可直接复用，实际发送记录只描述提交给通道的内容及其传输结果。Markdown 降级为源文本与纯文字化是不同策略，不能混为“已渲染”。

调用插件选择表格转文本等展示转换；通道只负责协议所需编码和平台长度检查。生成图片/PDF/XLSX、复杂排版或媒体转码由工具完成；不在基础 channels 中引入 Office、绘图或编解码运行时。

钉钉 AI 卡片承载一个文字块；完成后可以继续发送图片、文档和下一段文字。不能把完整文件塞入 Markdown，也不承诺多条平台消息呈现为同一个聊天气泡。每个块结束时提交最终完整内容；已创建的卡片失败时更新原卡片，不能自动重发整条回答。

## 8. 持久文件、会话与下载

本次附件 ID 是访问句柄，不等于永久文件地址。需要历史查询的交付物由调用插件保存至 filesystem 自己的空间：

```text
deliverables/<reply-id>/
├── manifest.json
└── files/<artifact-id>/<safe-name>
```

这是调用插件可采用的正式持久化约定，不是基础插件自动创建的目录。示例会实现一份具体策略，公共插件仅输出真实内容引用和回执，不要求所有调用者使用 JSON 或同一数据库。

manifest 记录内部 ID、owner plugin、可信用户/会话引用、名称、MIME、大小、校验和、相对文件引用、创建/到期时间及交付回执。会话与交付索引归调用插件，不加入框架 state.sqlite3。文件采用不可变内容，先原子落盘，再提交 manifest；失败留下的临时对象由同一插件清理。

需要跨重启辨别发送状态的调用插件，必须在首次发送前持久化本次发送意图和 attempt ID，随后写入各项回执。恢复时未闭合的 attempt 归为结果未知；不能根据“没有成功回执”推断一定未发送。上述记录不触发自动重试或恢复模型运行。发送成功但回执写盘失败也不能作为重发理由。

读取历史时由调用插件根据当前身份检查归属，再为本次响应登记新的附件句柄。HTTP 保留现有认证下载接口，长久文件的装载通过插件提供的受限读取器接入。签名 URL、机器人 media_id、会话 webhook 不作为永久引用保存。

默认重启不继续上一轮模型执行。已持久保存的文件可查，正在发送且未获得确认的条目标为结果未知，不自动重发。仅文件已保存、且尚未创建发送意图的记录可显示为未发送；会话删除、到期清理、显式保留由业务插件决定。没有配置持久存储的调用仍可发送临时附件，但须明确不提供重启后的历史下载。

## 9. 生命周期、审批与失败

逻辑范围为：调用准入 → 建立必要资源 → 执行/收集 → 交付 → 清理 → 释放调用。流式执行与交付可以交错；HTTP 的处理资源与传输占用按下文分别结束，不能把 handler 返回等同于请求生命周期结束。

所有创建的依赖作用域覆盖真实消费与附件读取。取消关闭源流并停止后续发送；有限时间内尝试标记已出现卡片中断。清理异常附加到原异常，不能覆盖首次失败。

交付结果统一描述为：prepared（已物化尚未写出）、written（已写入传输）、confirmed（平台明确接受）、failed（明确拒绝）、unknown（是否接受无法确定）。confirmed 不等于对方已阅读。HTTP/SSE 本地写出最多是 written，不伪造 confirmed；需要客户端确认的业务自行提供确认协议。每个结果保留逻辑 message ID、段位置、平台回执与转换信息，HTTP 断连和平台请求超时保留 unknown 或此前已完成的结果。

HTTP 业务 handler 返回时 JSON 响应可能仍未写出，必须由原生响应发送生命周期产生传输结果，不能在 MessageOutput.send 中提前记录 written。观察记录通过第 9.1 节的通道调用级回调接入，复用框架的归属和调用准入，不引入另一套全局事件总线。SDK tracing 也不能当作投递回执存储。

传输结果回调的插件归属和调用占用必须延续至回调完成，不能向已卸载插件调用旧函数，也不能复用 handler 已关闭的数据库会话。回执写入使用调用插件明确提供的短生命周期存储操作，失败单独记录，不覆盖已经发生的投递结果、不触发自动重发。普通 on_called 只能观察其真实覆盖的操作阶段，不能冒充后续 ASGI 写出回调。

### 9.1 HTTP 处理与传输的两个作用域

- 处理作用域：持有 Matcher/Depends 资源、SDK 运行、沙箱和输出迭代器；完成消费、固定附件后关闭这些资源。清理失败不能输出成功的请求完成标记。
- 传输作用域：持有待写出的不可变消息、回执关联信息及原调用的插件依赖占用；覆盖实际 ASGI 写出、断连收尾和可选回执观察函数，不持有已结束的 handler 数据库会话或沙箱读取器。

channels 在原调用仍有效时，通过现有 hold_continuation 将已准入依赖的占用接到传输作用域自己的 AsyncExitStack。实际写出与回执回调所在任务进入 invocation_scope，并恢复相应 plugin_scope。不能仅依靠 ContextVar 自动复制到子任务，也不能在处理调用结束后重新申请一个可能已被停用的插件调用。

JSON：处理完成并清理资源 → 原生 Response 实际写出 → 记录传输结果并调用可选观察函数 → 释放传输占用。SSE：边处理边写出 → 处理完成并清理资源 → 输出 done 或错误终止信息 → 结束传输并完成回执收尾 → 释放传输占用。done 表示处理及其清理完成，不代表客户端已收到，也不等待针对 done 自身写出的回执而形成循环。

回执观察函数是调用级可选参数，由需要记录的智能体插件提供，绑定已准入的所属插件；不建立全局订阅中心，不向无关插件广播。channels 在真实传输边界调用它，框架负责归属、准入和排空。观察函数只能记录结果，不能再向已结束的回复写入消息；使用新建的短事务或文件操作，不捕获 handler 依赖对象。观察失败单独记录，不改变已发生的投递结果。

所有任务均在上述作用域内等待结束；断连、取消或停止插件时，停止后续业务发送并执行有界收尾。若清理尚未结束，不得先撤销插件占用再留下任务继续访问资源；沿用框架的停止失败/未完成调用语义，不新增后台重试或“保证落库”队列。

### 9.2 平台发送操作与聚合回执

一个逻辑消息可以对应多次平台操作。每条操作结果至少关联 reply/attempt、message ID、原消息段位置、操作序号、操作类型及目标平台对象 ID（已知时），并保留状态、错误与原生响应。操作序号在本次 attempt 内递增；类型区分消息发送、卡片创建、卡片更新和卡片结束。媒体上传成功只是准备结果，不能当成用户消息已交付。

例如一段文字拆成三条发送，前两条确认、第三条超时：保留两条 confirmed 和一条 unknown，整体显示部分交付且存在未知，不能覆盖为全失败或全成功。卡片创建确认而最终更新失败时，记录最后成功提交的位置及失败操作，不将整段内容标记为已交付。

HTTP 可按完整消息或文字块记录累计写出位置与结束状态，无需为每个 token 持久化一条记录；流中途断开时保留已写出的前缀并标记未完成。完整回复成功要求所有必要发送操作结束且达到该传输可确认的级别：HTTP 最多 written，机器人平台接受可为 confirmed。不存在一个跨所有通道都表示“用户已收到”的成功状态。

### 9.3 审批续接与交付引用

SDK 审批中断由原生 RunState/interruptions 处理；尚未执行的工具不得产生“已生成”交付物。最终输出 guardrail 需要整体检查的插件采用 buffered 发布策略，通过检查后再发送。progressive 策略允许提前显示正文，必须明确后续失败无法收回已发送内容；这项发布决策属于调用插件，不能由通道猜测。

buffered 限制同时作用于正文和交付物：选中、登记或保存文件不等于授权公开下载。通过最终检查前不签发对外下载句柄、不发送附件；检查失败后的临时文件按调用插件策略清理。progressive 策略只发布已完成且明确允许公开的内容，不暴露审批中的工具产物。

审批可能发生在部分工具已经生成文件之后。支持续接的智能体插件在结束本次处理前，保存原生 RunState 及自己管理的交付引用信息：已固定文件、稳定业务引用、来源关联、选择顺序和已交付位置。后者不是原生 RunState 自动保存的内容，不能将闭包、读取器、客户端或调用级 Deliverables 序列化进去。

下一次经过身份和审批权限校验后，插件重新建立资源和交付集合，将稳定引用映射到本次附件句柄，再按原生 SDK 方式恢复运行；不重发已确认交付的内容，结果未知的发送不自动补发。buffered 模式仍暂存未公开产物，等待最终检查；恢复时文件缺失、过期或无权限则明确失败，不能按旧沙箱路径重新读取一个可能已变化的文件。

本方案中的 chat/sandbox 示例默认不提供审批续接：遇到 interruptions 明确告知未完成，不把它当作成功结果，不发布缓冲内容，并清理未保留的文件。需要审批的实际智能体插件按上述约定实现；使用框架 pause/reject 只解决交互，不自动保存 SDK 状态和文件引用。不跨请求保持运行作用域，也不因保存审批信息而恢复重启前的执行调度。

以上为目标职责树，保留实际需要的现有文件；不要求无关模块随之改名。删除原 messages.py 和 conversation_support/streaming.py；公开 import 由新的 messages/__init__.py 正式导出，不提供旧字符串流转换适配器。通用消息接口通过 channels 公开；SDK 结果由智能体插件直接消费，不增加输出插件依赖。

conversation_support 仅共享仓库内两个示例的代码。生产智能体插件在自己的包中实现与其输出类型、工具和沙箱相符的处理，不导入 examples。简单插件不需要 deliveries.py 或文件工具；有文件交付的插件采用对应内部模块。若 outputs.py 的职责增长，再按结果转换、流消费和产物读取拆分内部文件，不预先堆叠目录层次。

调用链为：

```text
框架 on_* / Depends
→ 智能体插件取得 Agent、用户与本次资源
→ execution.run / execution.stream 返回原生 SDK 结果
→ 插件自己的 outputs 选择并转换公开内容
→ Matcher.send/finish 或 Channel.call("stream")
→ channels 校验、编码和传输
→ 插件按自身策略保存文件与交付记录
```

保存与发送的时序遵循第 8、9 节：需要跨重启记录时，文件及发送意图先落地，实际回执在传输后保存；上图只表示调用职责，不表示所有持久化都发生在发送之后。

最终实现提供 chat 与 sandbox 两个完整示例，展示调用级工具绑定、框架注入、原生结果消费和资源关闭；不把示例内部函数当作新增公共 SDK。

6. 同一发布批次升级 channels、示例与服务器调用插件；替换文档中的旧 stream 示例。新旧代码不混装，无兼容分支。

## 12. 验收标准

- 完整回复覆盖 text + markdown + image + table + file，实际顺序一致。
- 自定义工具、原生 SDK 图像结果、沙箱文件均可登记；分析用途的工具图片不会被误发。
- 未登记 ID、伪造路径、逃逸链接、超限内容和不合法表格在相应边界失败。
- 流中正文—图片—正文—文件正确排序；重复完成事件不重复发送，嵌套消息和乱序增量被拒绝。
- 所有内容类型均覆盖 HTTP JSON/SSE；客户端不能只显示 text 而丢掉其他内容。
- QQ/钉钉覆盖媒体权限拒绝、长度与次数限制、部分成功、超时未知；不支持的消息明确拒绝，插件转换后再发送。
- 工具/SDK/发送/清理的失败与取消都关闭资源；首次错误保留，不重复发送。
- 最终 guardrail、审批中断及 handoff 不泄漏未批准内容；buffered/progressive 分别验证。默认示例在审批中断时明确结束；支持续接的调用插件另外验证重建资源、稳定文件引用和不重复交付。
- 重启可查询已保存产物，下载权限和过期策略正确，不恢复旧模型执行。
- 多用户、多会话并发不串附件、不复用他人的产物选择；停止插件能排空或报告未完成调用。
- 在完全没有 examples 路径的安装环境中，一个自包含的智能体插件仅依赖所需的正式基础插件及 SDK 即可交付内容；不依赖额外输出插件。检查 channels 不导入 SDK、execution 不导入 channels、生产插件不导入 examples。
- 缓慢通道、原生 SDK 快速生产、消费者提前退出时，输出预算和停滞超时能取消本次运行；检查 SDK 与适配器任务全部结束，不以“队列有界”替代进程内存验收。
- HTTP JSON 物化、SSE 写出、机器人平台接受分别验证回执；无客户端确认时不能报告客户端已收到。
- 在发送意图提交后、请求写出后、平台确认后及回执落盘前分别注入进程退出，恢复分类正确且没有自动重发。
- 选中文件后修改或删除原文件，实际发送和保存内容保持一致；选择过程中发生超限、读取失败或并发改写时不产生有效交付引用。
- JSON 返回前、SSE 尚有待发数据及回执记录期间停止插件，传输占用仍有效；完成/取消后任务、占用全部退出，清理失败不得提前释放正在使用的插件。
- 分段发送部分成功、卡片创建成功但结束失败均能定位实际操作；多次记录不会覆盖既有确认结果，不为每个 token 增加持久记录。
- channels 的交付集合不存 SDK 来源标识、不执行工具排序；纯文本插件无需创建该集合。无回执观察函数时不进行持久化。
- 自动化采用原生确定性 SDK 模型与模拟传输；机器人真实渲染单独验收，不以单元测试替代。

|---|---|---|
| 为 SDK 与 channels 的组合新增独立输出插件 | 把智能体插件自身职责拆成额外依赖与公开协议 | 第 3、5.4、10、11 节：结果解析、产物选择及文件工具归智能体插件内部，不新增发行包 |
| 把示例输出处理和通用消息能力混为一类 | 误把业务处理提升为基础插件，或让通用消息只存在于示例 | 第 3、5.4、8、10 节：channels 提供消息与附件契约，智能体插件内部按输出、工具和持久化分工 |
| 声称下游背压保证 SDK 整体有界 | 原生运行可能独立生产并累积事件 | 第 6、12 节：明确保证边界，任务预算、停滞取消和压力验收 |
| HTTP 写出被视为已确认交付 | 审计与重启恢复可能错误报告用户已收到 | 第 9、12 节：区分 prepared/written/confirmed 与真实发送生命周期 |
| 未规定发送前持久化意图 | 进程退出后可能把已发送但未记账的内容当作未发送 | 第 8、12 节：attempt 先记录，未闭合恢复为 unknown，禁止自动重发 |
| 未明确供应商文件读取和沙箱路径边界 | 错用客户端、凭据生命周期或宿主路径；不能证明可导出范围 | 第 5.2 节：受限读取函数、真实后端校验、未知来源拒绝 |
| 直接广播所有助手 token/结构化 JSON | 可能公开工具轮次正文或尚未校验的业务结果 | 第 5.3、9 节：公开内容策略、结构化结果完成后转换、原生审批边界 |
| HTTP 清理与最终回执共用模糊的作用域 | 依赖已释放后调用旧函数，或等待自身回执而无法结束 | 第 9.1 节：分离处理资源和传输占用，复用框架 continuation |
| 选择文件后按原路径再次读取 | 保存与发送内容不同，文件引用不稳定 | 第 5.1 节：选择前固定内容，保存和发送复用同一份数据 |
| 审批中断丢失交付集合 | 恢复后引用失效或重复发送 | 第 9.3 节：插件保存稳定引用并重建资源；默认示例明确不续接 |
| channels 持有 SDK 来源映射 | 基础传输插件混入模型运行语义 | 第 5.1 节：来源、工具位置和去重归智能体插件 |
| 单个回执覆盖拆分与更新结果 | 部分发送或卡片更新失败被误报为全部成功 | 第 9.2 节：实际操作定位、累计写出位置和聚合规则 |

复核结论：职责表、内部接口、目录树、迁移清单和验收项均按“基础插件提供通用能力，智能体插件负责模型输出与交付决策”统一。没有新增输出插件，也不要求 execution 依赖 channels、channels 依赖 SDK，或让基础插件绑定会话存储。功能完整性仍按第 12 节验收；未声称支持所有 SDK 工具产物、所有平台模板或任意媒体编码。

实施前必须将已锁 SDK 的支持类型列为明确矩阵，并验证实际钉钉模板/账号权限及 QQ 媒体限制。未知能力不猜测、不静默降级、不以设计文档替代真实联调。

## 14. 对框架的影响与架构符合性

### 14.1 已核对的源码扩展点

| 现有扩展点 | 本方案的使用方式 | 核心修改判断 |
|---|---|---|
| src/opsmesh/messages/message.py | channels 的 Message/MessageSegment 继续实现框架抽象 | 不新增核心消息体系，不把 SDK 类型放入核心 |
| src/opsmesh/matchers/matcher.py 的 send/finish | 智能体插件发送完整回复；finish 保留原有控制异常语义 | 不修改完成语义，不将 handler 返回值改成回复 |
| src/opsmesh/adapters/channel.py 的 call/send | 传输流和平台发送仍通过通道操作 | 通道契约在 channels 内演进，不新增核心网络协议 |
| src/opsmesh/dispatch/execution.py | 复用 Matcher 的规则、权限、依赖注入及 admitted_call；处理资源仍交由框架关闭 | 不复制分发器，不增加另一套 Matcher |
| src/opsmesh/plugins/invocation.py | 复用 PluginCall、hold_continuation、invocation_scope 和 drain_plugin | 已具备独立延续占用机制；优先由 channels 调整作用域组合 |
| src/opsmesh/plugins/registry.py 的 plugin_scope | 传输观察函数保留真实所属插件，与既有调用准入组合 | 不引入单独的插件注册或生命周期管理器 |
| src/opsmesh/dependencies/ | on_* 处理器通过 Depends 获取调用资源，Context 仍只注入可信调用者信息 | 不把附件集合、Agent 或会话状态塞入 UserContext |

源码核对发现：当前 API 消息处理将调用占用与处理依赖放在同一 stack，并在 process 结束时关闭；SSE 的实际 ASGI 写出在另一个任务继续进行。因此第 9.1 节不是当前已具备的行为，必须修改 channels 的请求/响应资源管理。框架已有显式 continuation，不能为此再创建独立“发送租约系统”。

### 14.2 实际修改范围

| 范围 | 需要实施的内容 |
|---|---|
| 框架核心 src/opsmesh | 按当前源码不预设生产接口修改；增加或复用针对 continuation、停止排空及跨任务使用的受影响测试 |
| channels | 消息 schema、通用交付集合、流契约、平台编码、操作回执以及 HTTP 两段作用域；主要改动集中于此 |
| execution | 保持原生结果、SDK 清理和观测接口；验证消费提前退出及取消，不承担输出转换或交付记录 |
| filesystem / database | 复用现有基础操作；不增加交付物表、审批表或智能体索引 |
| 智能体插件与示例 | 原生结果转换、文件工具、公开策略、必要的保存与续接逻辑；仅实现自己使用的能力 |
| 客户端与部署文档 | 同步新的通道流与消息契约，明确下载、部分交付和调用方迁移 |

本方案改变 channels 的公开流式契约，属于插件接口变更；即使核心接口不变，调用插件和客户端仍须同步更新。回执观察是 channels 的调用级能力，不能把“已有框架 hook”解释为已经存在传输完成通知。Channel.on_called 保留操作返回后的原有含义，不延迟到 HTTP 写出结束，也不用它伪造最终回执。

若实现中发现现有 continuation 在真实传输任务中不能正确排空，先写能复现的针对性测试；只有确认是通用调用生命周期缺陷时才修正核心。不为消息、文件或模型产物增加核心特殊分支，不能为了回避核心缺陷在 channels 再维护一套插件状态。

### 14.3 架构结论与限制

按修订后的职责分配，方案符合当前框架的事件驱动、消息抽象、依赖注入和插件生命周期设计。入口与业务交互走 on_*；输出走 Matcher/Channel；SDK 执行交给 execution；内容选择和业务记录由智能体插件持有。内部传输流元素是 channels 操作的数据契约，不逐 token 分发成框架 Event；否则会引入不必要的权限匹配、广播和顺序问题。

结论基于源码边界核对，尚不是运行验证。实现验收重点是两个作用域的取消与排空、文件内容固定、审批引用恢复和分段回执。没有新增插件、全局产物中心、后台重试队列或核心状态表；上述约束通过第 12 节测试验证后才能确认实现符合设计。

## 15. 本地实现与验证记录

### 15.1 实际边界

- 框架核心、execution、database、filesystem 未新增生产代码；channels 复用现有 PluginCall、调用作用域与框架消息。没有新增插件、持久化引擎或重试队列。
- channels 提供消息段、类型化流、协议发送和可选 Delivery 观察函数；产物清单及呈现策略归智能体插件。消息发送返回原生平台结果，观察记录通过 Delivery 接收。
- HTTP 在实际 ASGI 写出后记录 written。JSON/SSE 发送期间保留调用插件及依赖占用，handler 资源独立关闭；机器人确认和卡片更新逐操作保留。回执记录异常只记录日志，不重发。
- SDK 消费、结构化结果转换和文件历史均在智能体示例内部。沙箱 publish_file 使用原生 function_tool，绑定本次会话和附件集合；通过 Agent.clone 加入工具，不修改共享 Agent.tools。
- 示例默认 buffered；progressive 明确允许助手正文提前公开，遇到结构化 Agent 时拒绝逐 token 发布。审批续接未在示例开放，原生 interruptions 不作为成功结果。
- 示例的附件显示策略明确为：正文后发送工具显式选择的文件，再发送本次原生图像生成结果；各组内部维持选择或 SDK 条目顺序。示例禁用并行工具调用，不引入通用的并行工具排序器。定制插件可通过有序 Message/文字块指定其他展示位置。
- sandbox 文件在发送前落地为固定字节及 manifest，结束后的回执继续落盘。未闭合意图保持 unknown；/files 查询，显式重新交付生成新 attempt。清除会话历史及重置工作区保留已交付文件，删除会话删除文件；下载句柄另按通道 TTL 过期。
- 客户端展示有序文本、Markdown 源码、表格和媒体引用；可通过 --download-dir 保存文件，不携带凭据访问任意外部 URL，不跟随重定向、不覆盖已有文件。

### 15.2 原生 SDK 支持范围

本地验证版本为 openai-agents 0.24.0、openai 3.46.0；没有另造 SDK Result、Session 或 RunState。

| 来源 | 示例处理方式 |
|---|---|
| 原生文本 delta / done | 单一消费者，按响应与内容身份补齐，避免重复最终文本 |
| final_output 字符串 | buffered 等待最终校验完成后发布；格式由插件配置指定 |
| 结构化 final_output | 调用插件提供 Message 转换函数；禁止直接直播中间 JSON |
| ImageGenerationCall | 支持完成状态的 PNG/JPEG base64，按来源 ID 去重，解码前检查大小 |
| 自定义工具、MCP 返回图片 | 不自动公开；工具或智能体插件明确登记、选择后发送 |
| 沙箱文件 | 示例 UnixLocalSandbox 的原生 read_bounded，拒绝绝对路径与逃逸路径，固定读取结果 |
| 供应商 file_id、其他沙箱后端、其他图像编码 | 不猜测读取方法；调用插件需补充受限读取与对应验证 |
| 音频、视频 | 通道支持；调用插件提供真实时长、封面及符合平台的编码，不自动转码 |

### 15.3 验证与尚未验收事项

受影响自动化覆盖混合消息顺序、错误流关闭、原生 SDK 文本及图像条目、结构化输出、guardrail 拒绝、审批中断、文件固定与重建、API 媒体类型校验、下载地址约束、机器人部分发送、钉钉卡片及取消。JSON/SSE 在 ASGI 2.0 与 2.4 下验证 handler 结束后停止插件，实际写出和观察函数仍持有正确调用占用，结束后释放。

验证使用原生确定性 SDK 模型和模拟传输，没有调用真实模型或向机器人发送消息。未部署服务器上的 opsmesh_boss；调用方必须同步迁移类型化流。真实卡片模板权限、机器人渲染、Linux 沙箱端到端、进程强杀时序及持续负载压力仍需部署验收；本次不以单元测试代替这些结论。

## 通道职责收拢

- 沿用框架 Message、Event、Adapter、Matcher 和 Depends，不建立平行消息框架。
- Deliverables 位于智能体示例的 files.py；SDK 输出解析、产物持久化、格式选择和缓冲由示例负责。
- channels 的 sending.py 做公共预检，各平台做协议限制校验和编码。完整消息不再经过多层重复规范化。
- HTTP 的 server.py、requests.py 位于 api/；MessageExchange 负责一次消息请求，MessageOutput 负责消息编码与预算，响应对象负责实际 ASGI 写出。
- 普通 HTTPRoute 与 MessageRoute 分别保存所需契约，共用归属、路由冲突和撤销机制。
- 文件预算检查通过后才提交下载缓存。内容预算在 JSON/SSE 中使用相同口径，附件字节另有限额。
- JSON/SSE 使用相同执行期限，流使用空闲期限，网络请求使用协议客户端期限，不再给机器人文本块硬编码整体 60 秒上限。
- 有界队列只让可执行的会话队首占用工作槽；QQ、钉钉共用事件消费代码。
- 配置结构解析一次，凭据与账号占用由各协议模块检查；钉钉连接复用 token，有效期内合并并发获取。
- 确定性校验发生在发送前，明确平台拒绝与不确定传输失败分开记录，清理不覆盖首个异常。
