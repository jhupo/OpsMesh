# 扩展插件在线管理方案与内置 channels 架构审查

服务的发行包、源码归属、管理入口和迁移批次以[框架库与插件管理服务设计](framework-service-design.md)为准。本文保留在线操作与通道审查的细节。

v0.5.8 中，已登记扩展可在线查询、加载、停止、恢复和重启资源。CLI 使用 `--online-plugin-action <动作> --module <完整模块名>`。内置身份由各插件包声明。在线制品登记、持久操作记录、配置回退、卸载和 Worker 切换仍是后续设计。现行命令见 [Linux 部署](../linux-deployment.md)。

## 1. 运维边界

**现有的在线资源启停和未来的代码更新、卸载只面向普通扩展。** 内置插件的代码、依赖和插件级资源随宿主部署维护。当前仓库的内置插件范围取六个随项目发布的包：channels、execution、database、filesystem、knowledge、cron。安装可以按需进行。管理端可查询其状态；要更换内置版本、应用需要重启内置实例的配置或改变其启用策略，进入宿主维护流程。

例如，扩展 A 使用 channels 声明 QQ 账号，扩展 B 使用 channels 声明钉钉账号。停止 A 时，A 的 QQ 连接停止接收，已有调用完成回复后关闭连接；B 继续接收消息。重新启动 A 会重新构造 A 的连接。整个过程中 channels 插件本身、已启动的内置提供方以及 B 的生命周期都不发生切换。若修改的是 QQ 协议实现或内置 SDK 版本，应随内置包离线发布。

| 目标操作（含未实现项） | 内置插件 | 已准入的普通扩展 |
|---|---|---|
| status / 依赖影响预览 | 可查询 | 可查询 |
| register / load | 由部署、宿主启动策略决定 | 在线登记受信任的制品、加载声明 |
| stop / start（恢复）/ restart | 由宿主生命周期管理 | 对运行中的宿主在线执行。停止后关闭准入，显式 start 恢复，restart 在一次操作中先停后启 |
| enable / disable | 由部署、宿主启动策略决定 | 在线改变持久启用意图，与本次运行状态分别显示 |
| save / apply-config | 部署侧准备配置，需重建内置实例的变更在维护期生效 | 可保存候选并重建该扩展拥有的资源 |
| update / uninstall / reinstall | 拒绝，包括级联和同名替换 | 受依赖、资源清理及运行模式约束；成功条件见第 4 节 |

### 如何识别与执行政策

现有 `PluginRecord.protected` 同时要求 enabled、autoload、required 为真。内置插件允许按需安装，因此在各自的 `pyproject.toml` 中声明 `opsmesh.builtin_plugins` 入口点。宿主在导入插件代码前读取包元数据，将标记合并到现有运行时 `protected`，无需修改 SQLite 记录、`host.json` 或业务 `settings.json`。部署仍只安装受信任的包。[channels 包配置](../../packages/channels/pyproject.toml) · [存储模型](../../packages/service/src/catalog.py)

宿主根据已安装包的元数据保护规范模块名及其子模块。Host 阻止对应的在线变更，Driver 和注册表沿用运行时保护。宿主启动、整体关闭及启动失败清理沿用内部生命周期。后续实现在线制品登记时，再校验候选制品来源及命名空间冲突。

计算级联时只把**实际要改变运行状态**的插件放进变更集合。扩展依赖已就绪的内置提供方时可以启动；依赖的内置提供方未就绪时返回所缺依赖，禁止利用现有递归 start 顺带启动它。若某内置消费者会因停止扩展而必须重启，则执行任何停止之前拒绝整个操作，返回依赖链。[生命周期](../../src/opsmesh/plugins/activation.py)

## 2. channels 与框架的职责是否吻合

框架的 Driver 提供事件分发、插件生命周期和调用准入，不持有适配器或连接。channels 插件内部由 Adapter 管理连接，Channel 将平台输入转换为框架事件并调用分发接口，同时负责发送与连接清理。FastAPI、QQ 和钉钉协议均由 channels 实现；通道提供方不负责插件更新或包管理。[框架事件](../../src/opsmesh/events.py) · [通道 Adapter](../../packages/channels/src/adapter.py) · [通道 Channel](../../packages/channels/src/channel.py)

| 看起来相似的实现 | 应当保留的区别 |
|---|---|
| 已准备连接与在线状态 | `ChannelAdapter` 在握手前就要定位连接、阻止重复账号，清理失败时还要保留旧实例。由连接自身报告是否就绪，不额外维护 Driver 在线索引。见 [ChannelAdapter](../../packages/channels/src/adapter.py) |
| 框架准入和协议入口的 ready 检查 | SDK 的前置检查可尽早拒绝并返回平台 ACK；入队时仍需持有插件及依赖直到分发清理结束。握手完成、插件 READY、在途可回复分别表达不同条件。见 [回调分发](../../packages/channels/src/callbacks/dispatch.py) |
| API 监听与机器人连接 | HTTP 有监听端口、响应流和上传；机器人有长连接、去重、队列和平台确认。现有 CallbackChannel 已覆盖两个机器人协议的共同生命周期，APIChannel 保持独立。见 [通道基类](../../packages/channels/src/channel.py)、[APIChannel](../../packages/channels/src/api/channel.py) |
| QQ 与钉钉发送逻辑 | QQ 回复序号、条数限制归 QQ；钉钉 AI 卡片的增量更新与 ACK 归钉钉。消息预处理和流式遍历已有公共实现。见 [消息预处理](../../packages/channels/src/sending.py)、[流发送](../../packages/channels/src/streaming.py) |

### 优化项及改动尺度

| 优先级 | 具体发现 | 修改建议与验收 |
|---|---|---|
| 通道回归验收 | 钉钉初始化失败只能标记当前连接失败，仍需通知等待者并清理任务引用。[DingTalkStream](../../packages/channels/src/dingtalk/stream.py) | 注入初始化异常，验证 `wait_closed()` 能结束且其他插件继续工作 |
| 通道回归验收 | QQ 入站任务结束不得把致命失败覆盖成普通断线。[QQStream](../../packages/channels/src/qq/gateway.py) · [CallbackChannel](../../packages/channels/src/channel.py) | 验证握手前停止、断网重连、致命错误后查询状态，以及显式关闭 |
| 合并相同配置约束 | 两个机器人设置重复定义队列容量、并发、去重、请求及关闭超时；`ConnectionSettings` Protocol 又列出了部分字段。[QQ 配置](../../packages/channels/src/qq/config.py) · [钉钉配置](../../packages/channels/src/dingtalk/config.py) | 提取无协议依赖的机器人公共配置模型，由两个现有公开模型继承；可用于 CallbackChannel 的类型约束并移除重复声明。保留字段名、默认值、错误位置与协议专属范围，如两个不同的 max_message_length。公共模型放在不导入协议模块的叶子文件以避免循环导入 |
| 删除短小的重复实现 | 两个 Channel 仅凭据引用字段、错误类型不同，取环境变量、去空白、报错完全相同；两个 `_close_resources` 都只调用 client.close。[QQChannel](../../packages/channels/src/qq/channel.py) · [DingTalkChannel](../../packages/channels/src/dingtalk/channel.py) | 共用一个读凭据函数，保留两个配置异常类型和 disabled 跳过读取的行为；在现有 CallbackChannel 给出关闭客户端的默认实现。协议保留自己的客户端构造和任务创建 |
| 合并相同发送步骤 | 两个 Adapter 的 stream 分支重复校验 format、创建或沿用 Delivery、检查归属、把 message_id 传给发送器。钉钉另有 card 分支；钉钉的消息与通知入口重复把入队结果转成 ACK。[QQAdapter](../../packages/channels/src/qq/adapter.py) · [DingTalkAdapter](../../packages/channels/src/dingtalk/adapter.py) | 在现有 streaming 模块中抽取机器人发送适配函数，接收发送回调及可选 card 回调。ACK 转换用钉钉模块局部函数即可。验证分段顺序、delivery 所属检查、无卡片时聚合、有卡片时增量及队列满时的 ACK |
| 收紧插件依赖的框架内部接口 | channels 为连接挂 Hook 和回滚注册，直接引用 registry 中的 plugin_scope、track_registration。框架若调整归属规则会连带影响通道。[连接声明](../../packages/channels/src/adapter.py) | 首先明确这两个函数是否作为插件作者公共契约；需要稳定使用时从框架插件 API 导出并补契约测试。保留现有 owner 归属和“只有清理成功才能重建”的语义。无须再建一套通道注册中心 |

建议将上述正确性修复与机械去重分开提交。去重只在两个调用者具有相同输入、输出和异常语义时做；API 请求、QQ 回执与钉钉回执分别断言。验收依据是公开配置兼容、连接的状态和回复时序一致、共同规则只维护一处。

## 3. 接通扩展在线加载、启停与配置应用

1. **管理入口。** 安装命令和 `python -m opsmesh.service.cli` 使用同一个入口。部署服务由 `serve()` 运行，负责 systemd 通知和受文件权限保护的本机控制套接字。`load_host()` 直接返回装配后的 Host，CLI 和控制接口使用 Host 方法。在线 CLI 请求持锁宿主，离线 CLI 通过同一个宿主上下文进行维护。扩展停止后仍可查询；对从未加载的扩展执行 stop 返回明确错误。[CLI](../../packages/service/src/cli.py) · [Host](../../packages/service/src/host.py) · [服务](../../packages/service/src/service.py)
2. **热加载。** 对尚未导入且依赖兼容的扩展，先准备独立的可信制品目录，核对清单、来源、模块名及与宿主共享依赖的版本，再 register → load → 按需 start。load 仅完成声明和归属登记；start 才获取资源。导入或启动失败分别回滚本次注册或本次激活并记录失败。导入失败存在未清除的 Python 副作用时，标记该制品需新进程重试。要求可替换或有冲突依赖的扩展首次加载就采用第 4 节的 Worker 模式。
3. **资源管理。** 复用 Host、PluginManager 和 Lifespan。stop 临时停止；disable 持久禁用。先验证依赖和内置保护，再关闭新调用、排空在途请求和 finally，最后释放资源与激活期注册。清理失败保留资源引用并阻止二次启动。显式重启一组扩展时按依赖逆序停止、正序启动，只恢复先前运行的集合。状态查询分别返回启动意图、实际状态、在途数、清理进度、连接就绪情况。
4. **操作一致性。** 每次变更带 request_id、完整模块名和可选预期修订，重复请求返回同一 operation_id；同一 ID 参数不同返回冲突。宿主排队执行，CLI 断线不取消已受理操作。在现有管理锁内重新计算影响范围，SQLite 使用短事务记录阶段；关闭宿主先停止接收管理请求。报告失败阶段、阻挡依赖及是否可重试，日志避免记录配置秘密。
5. **扩展配置回退。** save 存候选快照，apply 时记录旧生效修订和运行集合。候选校验失败保留原实例；停旧失败阻止启动新实例；候选启动或所需连接握手失败，先清理候选，再用原快照恢复。清理或回退失败则停在可诊断状态。对已停扩展的 apply 只选择下次启动的修订。分别显示候选、启动选择、最后成功配置；显式说明仅保存候选在下次宿主启动时也不会自动生效。内置提供方自身配置走维护流程。

### 在线停止与恢复契约

停止和恢复是首期能力，由同一个服务进程完成。以下流程适用于同进程扩展，可复用现有生命周期，不依赖第 4 节的 Worker。

| 动作 | 运行行为 | 成功条件 |
|---|---|---|
| `plugin stop A --wait` | 进入 STOPPING，关闭新调用准入，排空在途请求，再释放 A 的连接、任务及激活期注册。保留同一版本的模块声明、配置和启动意图 | 返回 STOPPED 且清理完成。以后请求 A 应被拒绝，查询和恢复命令仍可使用 |
| `plugin start A --wait` | 清理完成、扩展已启用且依赖满足时，重新执行该版本的启动生命周期，从已选配置构造资源。复用已经就绪的内置提供方 | 返回 READY，并单列各连接状态。机器人可能仍在握手，通过状态查询或就绪等待确认可以接收消息 |
| `plugin restart A --wait` | 在同一管理操作内执行停止、清理和启动。清理成功后才创建新资源 | A 恢复服务，宿主 PID 和内置插件实例保持不变 |

显式 stop 保持到显式 start 或下一次宿主按持久启动意图启动。在当前宿主中记录人工停止标记，依赖递归启动遇到该标记时返回阻挡项，避免启动扩展 B 时悄悄恢复 A。A 恢复时只清除自身标记。如果管理员显式级联停止了一组扩展，返回已停止的集合，后续按依赖顺序恢复。重复停止已清理的实例、启动已就绪的实例均返回当前状态。清理超时后继续保留未完成项，可以在线重试停止，确认释放完毕后再恢复。

## 4. 扩展的卸载、更新和同名重装

**逻辑卸载。** 对目标、子插件和全部已加载消费者做预检，包括已停止但仍持有模块引用的消费者。持久记录“卸载中”，关闭新准入，按顺序执行 stop、排空、revoke 和撤除管理索引。保留禁止发现的记录，防止下次扫描入口点时重新登记。保留配置及业务数据。当前撤销实现可能在部分清理失败后仍删除索引，因此查不到插件不足以判定成功。无法证明释放完成时记录未完成项，限制再次激活。[注册撤销](../../src/opsmesh/plugins/registry.py) · [加载器](../../src/opsmesh/plugins/manager.py)

**代码替换的运行边界。** 同进程的 require 返回真实模块，Driver、Matcher 和扩展都可能持有旧类或回调。该模式支持资源重启和逻辑卸载；同名代码替换需要新解释器。为满足完整热更新，增加扩展 Worker 模式：宿主及已加载的内置提供方常驻，Worker 只装载目标扩展及其私有依赖。可共享框架的类型定义，禁止在 Worker 重启一份内置插件运行实例。扩展若直接互相引用 Python 对象，可将这组扩展作为一个部署单元并明确影响范围。

**跨进程适配是交付前提。** 宿主侧按扩展 ID 登记稳定的入口和资源，跨 IPC 传递事件数据、调用 ID、回复操作及取消信号。账号和 HTTP 监听仍由宿主内的 channels 按扩展所有者管理；通过调用 ID 查找在途准入并将回复送回原连接，调用完成或流清理结束后释放持有。需设计宿主侧代理注册和注销路径，继续使用原框架分发与生命周期，而非把 channels 移到 Worker。跨版本原子切换该扩展的路由，已受理的调用固定留在原版本。

第一批 Worker 扩展使用可序列化事件/消息接口。现有 `get_app(driver)` 暴露真实 FastAPI 对象，示例聊天插件还直接取得数据库引擎，这些原生对象无法直接跨进程。登记时记录运行模式和所需能力；遇到未适配能力明确返回阻挡项。按实际需求设计宿主能力接口或将扩展自有资源移入 Worker。兼容改造完成前，这类扩展可按现有同进程模型管理资源，不能宣称已支持同名代码热替换。[API 原生接口](../../packages/channels/src/api/__init__.py) · [示例聊天插件](../../examples/chat/example_chat/lifecycle.py)

**版本切换顺序**

1. 部署工具在独立目录准备可信扩展版本，校验摘要、兼容性、保留名和能力声明。新 Worker 在无线上流量状态启动并完成预检，独占副作用需等到宿主授权。
2. 同一个宿主连接可沿用时，先验证候选就绪，再切换后续请求路由，旧调用及流继续使用原 Worker 直到排空。若消费扩展的端口或账号配置也变更，则先关闭对应入口准入、排空、释放旧独占资源，再准入新连接；显示实际中断窗口。内置 channels 无须重新注册或激活。
3. 通过修订号检查、交接编号和活动版本指针标识唯一接收者。日志记录切换阶段；提交前失败则撤回候选，保留或恢复原路由。提交后回退作为独立操作。工作进程失联时关闭其新准入，并向受影响的在途调用返回明确的失败结果，不能盲目重放已产生副作用的请求。
4. 排空旧 Worker 并确认退出后再释放其版本引用。终止不响应取消的扩展 Worker 前记录未完成调用。版本目录无运行进程、无回退或共享引用且属于部署工具时，才允许物理回收。外部指定目录和业务数据单独管理。跨版本数据库迁移需具备回退兼容性，否则标记为维护升级。
5. 宿主崩溃恢复时对照持久活动版本、切换阶段和 Worker 身份，确认旧资源归属后恢复服务。当前机器人队列在内存中，跨进程/断连不承诺零丢失；需要可靠投递的部署应另外设计确认、持久化与幂等。

## 5. 发布、存储与验证

| 批次 | 实施位置 | 发布条件 |
|---|---|---|
| A. 固化内置政策与精简通道 | 插件包元数据、Host 发现和现有运行时保护；channels 的机器人公共逻辑 | 内置可选包可按需安装；通道故障与行为测试通过 |
| B. 扩展在线管理 | CLI、Host、Driver.Lifespan、storage、部署 unit | 独立 CLI 可在线登记、加载、停止并恢复扩展。实测同一宿主 PID 完成停止和恢复，管理接口、内置插件及无关扩展持续可用；Host 负责管理请求，Driver.Lifespan 只负责当前运行时的资源切换 |
| C. 配置回退与逻辑卸载 | app、storage、admission、registry、manager | 可恢复或明确报告失败；已卸载扩展重启后不会由发现流程复活 |
| D. 扩展 Worker 与能力适配 | 扩展进程入口、宿主代理注册、IPC、部署发布与回退 | 用两个真实扩展版本演示热更新、同名重装、失败回退及资源回收；内置实例全程存活 |

后续配置回退与卸载会从 SQLite v3 迁移，保留既有配置、保护字段和初始意图，增加安装状态、运行模式、候选/活动修订、制品引用和操作记录。区分首次配置尚未初始化与已保存的空配置。迁移在单一事务中执行并保留回退快照，状态库由宿主写入。部署时先交付 A/B，再开放 C，最后按已适配的扩展逐个启用 D。

**验收用例**

- 校验六个内置包的安装元数据及其已声明的子命名空间。分别从 CLI、进程内受支持的管理 API、同名注册、级联和依赖递归发起变更；检查请求被拒绝前后注册表、存储、资源和 generation 一致。宿主正常启动、关闭和失败回滚仍可工作。
- 真宿主运行扩展 A/B，在线加载 A，执行 stop 后确认已受理的回复可完成、新请求被拒绝，尝试启动依赖 A 的扩展时返回 A 已人工停止。通过 start 恢复 A 后发送新请求，确认只有一份连接和处理器生效。全过程核对宿主 PID、B 的响应，以及内置 provider 的对象身份、generation 和生命周期回调次数。验证清理失败后在线重试、同请求重试、CLI 断线和并发操作。
- 配置候选端口占用或握手失败时测试回退；清理失败时无第二连接。逻辑卸载后重启宿主，验证不会重新发现，共享 site 中其他插件仍能加载。
- 使用两个返回不同版本标识的扩展 Worker，在持续请求中切换；检查新请求的版本、旧流收尾、候选崩溃/提交前后宿主退出时的恢复结果。对使用未适配原生对象的扩展明确拒绝 Worker 更新。卸载并以相同模块名重装，验证旧回调和旧版本不会再收消息。
- 通道回归覆盖 QQ/钉钉失败与重连、关闭超时、API 流排空、已接收的队列项及消息/卡片发送顺序。已有基线的 32 项通过记录对应此前的生命周期、通道配置和排空测试；上述新功能与故障场景须在实施时增测。[框架生命周期](../../tests/unit/framework/test_plugin_lifecycle.py) · [通道配置](../../tests/unit/test_channel_configuration.py) · [通道排空](../../tests/unit/test_channel_lifecycle.py)
